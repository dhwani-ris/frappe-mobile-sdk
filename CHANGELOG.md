# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- **Child rows never sent their `mobile_uuid`, so the server stored it as NULL and a child had no identity across a round trip.** `PayloadAssembler` re-added the parent's uuid explicitly after the system-column strip (`mobile_uuid` is in `systemSyncMetadataColumnNames`), but the child loop seeded only `doctype` and never put it back — so the round trip was closed in one direction and open in the other, and the pull path's child adopt branch could only ever fire for a value someone had set in Desk. The server side was never the blocker: `mobile_control._ensure_mobile_uuid_fields` provisions the field on child doctypes as well as parents (verified `UNIQUE` on both, e.g. a duplicate write to a child table fails with MariaDB error 1062), and the parent has always sent it under the same `read_only` flag — which is the empirical proof the server accepts a client-supplied value. Each child now sends **its own** uuid, on INSERT and UPDATE alike. Three details are deliberate: it is the child's uuid rather than the parent's (reusing `row.mobileUuid` would collide on that UNIQUE index the moment a second child was sent); a blank uuid is **omitted** rather than sent as `''`, because MariaDB permits many NULLs in a unique index but not many empty strings; and no `set_only_once` concern applies, since that property does not exist on `Custom Field` in this Frappe version (it is declared only on `tabDocField`), so re-sending the same value on later updates is safe. This also retires the first load-bearing item in `ThreeWayMerge`'s row-level-child-merge plan, whose comment claimed the `Custom Field` install still needed extending; it did not, and the wire was the only gap. **Children written before this change keep `mobile_uuid = NULL` server-side and match by position until their parent is next pushed** — nothing backfills them.

- **A `media_cache` row could name a file that was never written, so the attachment re-downloaded on every view and its real bytes became unreclaimable.** `MediaStore.cachePathFor` borrows the extension from the SOURCE when the `file_url` carries none — its own docstring names the case, a `download_file` proxy url that keeps the filename in its query. `moveToCache` passed `sourcePath` and therefore wrote `<digest><ext>`, while `AttachmentPipeline` recomputed the path *without* the source and recorded `<digest>`. For an extension-less url the two diverged silently in both directions that matter: `MediaResolver` found the row, `File(localPath).exists()` was false, and it degraded to a cache miss and re-fetched — every view, forever — while the uploaded original sat at `<digest><ext>` where nothing reclaims it (`sweepOrphans` walks `outbox/` only, so short of `clearMediaCache()` it would linger for the life of the install). `moveToCache` now RETURNS the destination it actually used and the pipeline records that, so the two cannot drift again — the destination is not derivable from the url alone, which is exactly why recomputing it was wrong rather than merely redundant. `MediaResolver`'s own call site was already self-consistent (it computes the path once, writes to it and indexes the same value) and is unchanged.

- **Every HTTP 417 was classified terminal, which inverted the classifier's own stated policy and stranded files no retry would have failed on.** `isTerminalAttachmentError` documents "a wrongly-transient error costs one retry; a wrongly-terminal one strands the user's file with no automatic recovery. Fail toward retrying" — and then returned `true` for all of `ValidationException`. 417 is not the oversized-file status; it is where **every** `frappe.throw` lands, so a site storage-quota rule, a custom `File` hook or any transient server-side business rule became `rejected`, which is never auto-retried and blocks the parent document until the user replaces the attachment. The stated justification was also wrong: **an oversized upload never reaches 417 at all.** Frappe sets werkzeug's `max_content_length` to the same `get_max_file_size()` value (`frappe/app.py:194`), so the HTTP layer rejects first — verified against a live v16 bench, where a 30 MB upload returned `413 Request Entity Too Large` with an HTML body, which the SDK surfaces as an `ApiException` and the existing 4xx rule already classified terminal. Classification is now keyed on the exception Frappe **names** rather than on the status: `frappe/utils/response.py` sets `exc_type` unconditionally on a v1 error response and `RestHelper` hands the whole decoded body to `ValidationException.errors`, so this is structured rather than a substring guess (the v2 `errors: [{type}]` shape is read too, and a message-text match remains as a fallback for a body that carried no type). `MaxFileSizeReachedError` and `FileTypeNotAllowed` stay terminal; a generic `ValidationError` is now transient.

- **The `pending:` marker prefix had three literal spellings alongside the constant that exists for it.** `kPendingMarkerPrefix` was used by the writeback `WHERE` and by display resolution, while the producer (`local_writer`), `inlinePayload` — the "loud not silent" backstop — and `isLocalAttachmentPath`'s prefix list each hardcoded `'pending:'`. Nothing was broken, but changing the constant would have broken the two halves in opposite directions and both quietly: the writeback would match nothing, and `MediaResolver` would stop recognising the marker, fall through to `isLocalAttachmentPath` whose literal still matched, be told "not a local path", and issue the marker as an HTTP request — the one outcome that function's comment says must never happen. This release exists because markers reached the server; the invariant that prevents it is now enforced by the compiler at all five sites.

### Changed

- **`MediaStore.moveToCache` returns `String?` (the destination used) instead of `bool`.** Source-breaking for a host that calls it directly; `null` still means "neither source nor destination exists", so `!= null` is a mechanical migration. See *Fixed* for why the path has to come from the move rather than be recomputed.

- **`MediaResolver` gained `maxFetchBytes`, defaulting to the new `kDefaultMaxMediaFetchBytes` (25 MB), and `FormScreen`'s fetcher now streams.** Picks were size-guarded at 10 MB before staging but downloads were unbounded, on a device floor of API 26 where one attachment can take the process down. The bound is deliberately in two places because they solve different problems: `FormScreen._fetchMediaBytes` now uses a streamed request and refuses on `Content-Length` before reading a chunk (re-checking mid-stream, since a chunked response declares no length), which is the only place that sees the response before it occupies memory; `MediaResolver.maxFetchBytes` cannot prevent the allocation — by then the injected fetcher has already buffered — so its job is to keep an oversized body out of `cache/` and out of the index, where it would be re-read on every view. The download ceiling is intentionally higher than the pick ceiling: a Desk user may legitimately attach something larger than a mobile pick allows, and refusing to display it would be the worse failure.

- **`AttachField._fullFileUrl` and `ImageField._fullImageUrl` now delegate to `frappeFileFetchUrl`.** All three held the same logic; the helper's own NOTE recorded the duplication as a deferred follow-up. `/private/files/` has to route through `download_file` to carry auth, so a drift between the copies was a private-file 404. Behaviour is unchanged — the three were verified logically identical before collapsing — and the shared helper, which had no direct coverage, now has every branch pinned.

- **`kDefaultSyncBackoff`'s doc comment described an attempt count neither consumer had.** It claimed "3 attempts at 2s, 5s, 10s"; `AttachmentPipeline` loops `attempt < backoff.length` (3 attempts, and because the delay is taken only when another attempt follows, the final `10s` is never slept on) while `PushEngine` loops `attempt <= networkBackoff.length` (4 attempts, all three delays used). The loops are both correct for their own purpose and are deliberately left alone — making them agree would change push retry counts nobody asked for. The comment now states what each consumer actually does, and warns that trimming the list changes the pipeline's attempt count rather than only its waits.

- **A pulled document was stored under a freshly minted `mobile_uuid` even when the server round-tripped the one this device had assigned, so every local identity changed after any wipe.** `mobile_uuid` is in `systemParentColumnNames`, so the pull's meta loop never copies the server's value into the local column — and both parent write paths then minted unconditionally: `existing.isEmpty ? uuidGen.v4() : …` (sequential) and `existingUuids[serverName] ?? uuidGen.v4()` (bulk). Neither expression could ever yield the incoming value. The server's `mobile_uuid` *was* read, but only as a **matching key** to find an existing local row — never as a value to store. With a local row present both lookups hit and the local uuid was preserved, which is why this stayed invisible in normal operation; it surfaced only when the row was gone. `logout(clearDatabase: true)` drops every `docs__<doctype>` table, so the re-login pull missed on `server_name`, missed on the `mobile_uuid` fallback, inserted, and minted — giving the *same* server records brand-new local identities. Reinstall and fresh-device onboarding took the same path. **This defeated the very fallback the stored uuid exists for:** `mobile_control` provisions `mobile_uuid` as a `unique: 1` Data field (on parent *and* child doctypes) precisely so a row whose `server_name` writeback was interrupted can still be reconciled — unusable once the local value no longer matches. It also meant the cross-device uuid-clash tripwire could never fire for a re-pulled row, and that a server-side `mobile_uuid` identified only the session that created a document, not the device holding it. A non-empty incoming uuid is now **adopted**; an empty or absent one still mints, which is load-bearing rather than defensive — Desk-origin rows return `mobile_uuid` as null or `''`, `mobile_uuid` is the local primary key, and adopting `''` would write an empty PK that the next such row collides with. Precedence is now **local, then incoming, then mint**, and an existing local uuid still always wins: outbox rows and `pending_attachments` reference it, so a pull must never renumber a row that already exists. All four write sites (parent and child, sequential and bulk) route through one `resolvePulledMobileUuid` helper so the precedence cannot drift between them — the child paths already implemented this precedence correctly and are unchanged in behaviour, only deduplicated onto the shared helper. **Verified on a device, not just in tests:** a clean install and login against a live bench took the bulk path for the affected doctype and reproduced the divergence beforehand (2 of 3 records under fresh local uuids) and the adoption after (both now equal to the server's, byte for byte), while the third record — Desk-created, so `mobile_uuid` is null server-side — correctly still minted, exercising the empty-value guard on real data. Child rows stayed correctly parented to the adopted uuid with zero orphans, and the run was clean (603/603 HTTP 200, no exceptions). The round trip is now closed in both directions for children too — see the child-`mobile_uuid` entry above, which was split out of this one. **Parent adoption is additionally gated on UUID shape; child adoption is deliberately not.** Being UUID-shaped is an invariant the push pipeline depends on twice: `looksLikeMobileUuid` is what `UuidRewriter` calls "the complete detector" for a local Link reference (Frappe server names are never UUID-shaped, SDK uuids always are), and `PushEngine`'s dependency scan uses the same predicate to tier a row behind the row it points at. A non-UUID primary key is invisible to both — the rewriter falls back to `__is_local` alone, which its own comment records as insufficient for `fetch_from`, defaults, programmatic prefill and back-reference Links, and the dependency scan drops the edge so the row lands in its parent's tier and races it. Reachability is low, because a Link value only carries a `mobile_uuid` when the target row has no `server_name` and an adopted row always has one, but minting instead costs nothing and keeps the invariant true by construction rather than by argument. **Children keep the emptiness-only test they already had, and that asymmetry is history rather than taste:** child adoption is not new — the child paths have always taken any non-empty incoming value — and it is load-bearing, because a Link field on another document can reference a child row by its `mobile_uuid`, so a child whose uuid changed on re-pull left that Link a permanent orphan. That regression is pinned by `pull_apply_test.dart`'s "child mobile_uuid is preserved across re-pull", whose fixture uses a deliberately non-v4 uuid because deployments exist with exactly that shape. Gating children would re-break it, so tightening them needs its own change, evidence and migration rather than riding along here. Uniqueness is deliberately **not** re-checked client-side: `mobile_uuid` carries a real UNIQUE index server-side — verified by a rejected duplicate write (MariaDB error 1062) on both a parent and a child table — so two server documents cannot present the same value. **That is a precondition rather than a guarantee this package owns, and worth naming for that reason:** the index is provisioned by the `mobile_control` Frappe app — verified in its `_MOBILE_CUSTOM_FIELDS`, which declares `mobile_uuid` as a `Data` field with `"unique": 1` for every workspace doctype and its child doctypes — while this is a standalone package dependency that carries no `publish_to: none`, so nothing in this repo can enforce it. `mobile_uuid` is the local mirror's `PRIMARY KEY`, so a site that provisions the field without `unique: 1` and returns two documents under one value gets three different outcomes, exactly one of them silent. **Bulk parent path (initial sync only) — silent:** `ConflictAlgorithm.replace` resolves the PK collision by dropping the first document's local mirror, with no log and no error. The two documents then share one row for the life of the install, and which one the mirror holds flips on every later page that carries either — those later flips *are* logged by the cross-device-clash tripwire above, because the `mobile_uuid` fallback query now matches, so the unannounced window is the bulk page itself. The bulk safety pre-check does not prevent it: it counts locally-*dirty* rows and local-only rows, so a clean `synced` row is replaced without objection. **Sequential path, both rows in one page — loud:** its plain `INSERT`s are queued in `txn.batch()` and therefore invisible to that same fallback query, so both are queued and the second raises `UNIQUE constraint failed: docs__<doctype>.mobile_uuid` at `batch.commit`, where `continueOnError` is unset (extended code 1555 as observed under sqflite FFI; the message is the stable half). The transaction rolls the page back, and both pull paths then stop the doctype without advancing its cursor — `PullEngine` logs "failed mid-pull" and reports the doctype, `SyncService` logs and raises a `SyncError` carrying the message and the affected `name`s, and both `break` before their cursor journal writes — so the page is retried and re-fails every cycle until the data is fixed. Reported and stalled, not lost. **Sequential path, rows in different pages — neither:** the fallback matches the first document's row, the tripwire logs, and the second document's snapshot overwrites the first in place. Child collisions always take the loud path, the bulk child insert being a plain `INSERT` too. So the server-side index is a hard requirement rather than a recommendation, and the single unannounced event it guards against is the bulk page.

- **`ImagePickSource` and `MediaStoreUsage` were described as host-facing in 2.0.0-beta.2 but never exported, so the pick-source hook could not be wired at all.** `FormScreen.imagePickSource` takes a callback that must *produce* an `ImagePickSource`, and neither the enum nor its `allowsGallery` / `allowsCamera` extension was reachable from `package:frappe_mobile_sdk/frappe_mobile_sdk.dart` — so a host had no way to name the value it was being asked to supply, short of an `implementation_imports` violation. Every layer inside the package was wired correctly (`FormScreen` → `FrappeFormBuilder` → `FieldFactory` → `ImageField`, on both the parent and child-table paths); the feature was complete internally and unreachable externally, which is the same shape as an implementation with no callers. `MediaStoreUsage` — the return type of `FrappeSDK.mediaStoreUsage()` — was in the same position but less severely: type inference still let a host *read* `usage.orphanBytes`, it simply could not store the value in a field, return it from its own function, or write the type anywhere. Both are now exported; no signature moved and nothing else changes. **The test suite could not have caught this, because every existing test imports `src/` directly** — precisely what a host may not do. A new test that imports only the public entry point now fails to compile if either export is dropped.

- **`ResolveMediaFn` was not exported either, so a host could not override `FieldFactory.createField` at all.** The same defect class as the entry above, and missed by that fix. `FieldFactory` is exported bare from the barrel and its `createField` is documented "Override this method to customize field creation" — and that signature takes a `ResolveMediaFn? mediaResolver`. The typedef lives in `src/services/media_resolver.dart`, which the barrel did not export, and exporting `field_factory.dart` does not carry it: Dart re-exports a library's own declarations and whatever it re-`export`s, never its *imports*. Passing `resolver.resolve` as an argument always worked because the type is inferred; a host that had to **write the type out** in an override signature had no route but an `implementation_imports` violation. Now exported. Confirmed both directions: `public_api_surface_test.dart` fails to compile with `'ResolveMediaFn' isn't a type` when the line is removed, and a real consumer app that subclasses `FieldFactory` to keep read-only child tables tappable now analyses clean against the public barrel alone, with its `src/` workaround deleted.

- **`doc/release-2.0/attachments.md` listed `ResolveMediaFn` in its Host API table, which a host cannot name.** The row promised a type that does not exist on the public surface — see *Known issues* for the gap itself. Corrected in place, and cross-referenced from §10, which described hosts passing `resolver.resolve` without noting that passing works only because the argument type is inferred.

- **`doc/release-2.0/attachments.md` said the attachment pipeline was "not verified on a device", which is no longer true, and it attributed server-side image shrinkage to the wrong mechanism.** Both claims are corrected against a measured run on hardware (new §16). The compression note previously mentioned in passing that "Frappe strips EXIF server-side" alongside the `optimize` / `max_width` / `max_height` parameters the SDK does not send, which left the two conflated. They are now separated and each is grounded: `optimize_image` provably does **not** run (gated on a client-supplied form field the SDK never sends, and it would resize to ≤1024×768 while measured server copies kept the full 3120×4160), whereas `strip_exif_data` **does** run when a site enables `strip_exif_metadata_from_uploaded_images` — and it re-encodes through PIL rather than merely deleting a metadata block. The three measured consequences are now documented: the strip is **JPEG-only** (so PNG uploads stay byte-identical, which is why two gallery-picked screenshots matched to the byte while two camera JPEGs did not), **GPS EXIF is destroyed** (10 tags including `GPSInfo` → 0), and the re-encode is **lossy** (3,304,466 → 1,077,127 B at unchanged dimensions). This is a site setting rather than SDK behaviour or a Frappe default, and the doc now says so explicitly. The §13 and §15 "not verified on a device" claims are narrowed to what genuinely remains unexercised — `OpenFilex` handoff, camera lost-capture recovery, the logout wipe, and offline preview from `outbox/` — rather than covering ground the run now pins.

## [2.0.0-beta.2] - 2026-08-12

Second prerelease on the 2.0 line. Everything below was previously staged under
`[Unreleased]`; the heading is dated here so the published version and this file
agree, as `[2.0.0-beta]` does. Still a **prerelease** — `pub.dev` continues to
serve 1.2.0 as the default install, and this version is only resolved by asking
for it explicitly.

### Changed

- **`FrappeSDK.mediaStoreSize()` is replaced by `mediaStoreUsage()`.** A single number could not tell a host how much was actually reclaimable. Both are part of this same unreleased release, so nothing has shipped against the old name.
- **The attachment pipeline's resolution API changed shape — source-breaking for a host that drives it directly.** `AttachmentPipeline.uploadPendingForTopParent` is now `resolveForTopParent`, the constructor requires `db` (it writes the resolved `file_url` back inside a transaction), and `resolutionMapFor` is new. `PendingAttachmentDao.findPendingForTopParent` is now `findUnresolvedForTopParent`, joined by `findAllForTopParent` and `markRejected`. Hosts that only call `FrappeSDK` / `SyncService` are unaffected — `PushEngine` wires all of this internally.
- **`AttachmentPipeline.inlinePayload` now throws on an unresolved `pending:<id>` marker instead of passing it through.** The silent passthrough is what let the literal string reach Frappe (see *Fixed*), and it was indistinguishable from a legitimate value. Under the new push gate this should be unreachable; it throws so a future regression is loud rather than silent.
- **`resolvePickedAttachment` gained a `maxBytes` guard and now rethrows a terminal upload failure.** It previously returned the staged path for *every* failure. A transient failure still falls back to the staged copy for save-time queueing; a terminal one (oversized, wrong type, not permitted) discards the copy and rethrows, because queueing a file the server has already refused only guarantees a blocked push later.
- **Staged attachments now live at `mform_attachments/outbox/<id>/<original filename>`** rather than `mform_attachments/<uuid><ext>`, and uploaded bytes move to `mform_attachments/cache/`. The file keeps the name the user picked — uniqueness comes from the generated parent directory — because the original filename has no other route to the server (see *Fixed*). Staging and cache are separated because their safety properties are opposites: an un-uploaded staged file is the only copy in existence and must never be evicted, while a cached download is always re-fetchable.
- **Database schema v6 → v7.** Adds the `media_cache` table. Migration is automatic and backfills nothing — the cache is non-authoritative, so an empty table simply means every lookup is a miss and re-fetches on demand. No host action.

- **Swift Package Manager support (iOS).** The plugin's Swift source now lives at `ios/frappe_mobile_sdk/Sources/frappe_mobile_sdk/`, alongside a new `ios/frappe_mobile_sdk/Package.swift`; the podspec's `source_files` points there. Both build systems work — CocoaPods reads the podspec, SPM reads `Package.swift`. `Package.swift` deliberately declares no dependencies rather than a `FlutterFramework` path dependency, which would impose a Flutter 3.44 floor on every consumer.
- **The declared SDK range is now measured rather than nominal: `sdk: ">=3.9.0 <4.0.0"`, `flutter: ">=3.35.0"`.** The floor is set by a framework API, not a language feature — `lib/` uses `DropdownButtonFormField(initialValue:)`, which exists only from Flutter 3.35 (3.32 and earlier expose `value`). Verified by running `pub get`, `analyze` and the full test suite against Flutter 3.35.7, 3.38.10 and 3.41.5. This replaces the `flutter: ">=1.10.0"` placeholder, which satisfied publish validation but claimed support back to Flutter 1.x. There is deliberately no upper bound.
- **Dependency ranges widened, not bumped** — `geolocator` → `>=13.0.2 <15.0.0`, `package_info_plus` → `>=9.0.0 <11.0.0`, `app_links` → `>=6.4.1 <8.0.0`, `flutter_form_builder` → `>=10.1.0 <11.0.0`. All four are strict supersets of the previous constraints, so **no consumer is forced to upgrade**: an app on an older Flutter keeps resolving the older plugin versions while a current app resolves the newest. `package_info_plus 10.x` and `geolocator 14.0.3` are not yet reachable — `file_picker 11.0.2` pins `win32 ^5.9.0` while they require `win32 ^6` — but the ranges allow them, so they are picked up automatically once `file_picker` moves.
- **`DoctypeService.listFullDocsPage`'s return type gained two fields — source-breaking for one spelling.** The record is now `({List<Map<String, dynamic>> docs, int namesScanned, String? scannedMaxModified, String? scannedMaxName})`. Dart records have no width subtyping, so a host that **writes the record type out explicitly** (in a variable declaration, a field, a return type, or a record destructuring pattern) will fail to compile. Reading fields by name — `page.docs`, `page.namesScanned` — is unaffected, which is what every in-repo caller does. `DoctypeService` is exported from the barrel, so this is a real external surface change and not merely internal.
- **A doctype the server *terminally* refuses now leaves the mobile-form set.** When a pull fails with a 403 (this user cannot read it) or a non-gateway 5xx (e.g. a doctype missing its server-side controller), the doctype's `isMobileForm` is cleared so the request stops being reissued — the measured steady state was a 403 and a 500 recurring 5× each in a ten-minute capture. **Behaviour change, and the cost is real: demotion is not self-healing within a session.** Only `resyncMobileConfiguration` re-promotes, and the SDK calls it at login and `initialize()`, not per sync cycle — so a demoted doctype disappears from `getMobileFormDoctypeNames()` and from the workspace until the app is relaunched. The terminal set is therefore deliberately narrow: transport failures, timeouts, and the **gateway 5xx family (502/503/504)** never demote. That exclusion is load-bearing rather than theoretical — `bulkGetWithChildren` raises `ApiException(…, 502)` for a truncated or proxy-mangled `2xx` body (see *Fixed*), so treating 502 as terminal meant a single mangled response cost the user a form until restart. Pinned by tests in both directions.
- **`OAuth2Helper` now throws `ApiException` (carrying the HTTP status) instead of a bare `Exception` on a non-200 token or refresh response.** The status previously survived only inside the message string, so callers could not tell a dead grant from a dropped socket — see *Fixed* for what that cost. `ApiException` implements `Exception` and the message text is unchanged, so `catch (e)` / `on Exception` handlers are unaffected; only code matching on the exact runtime type sees a difference. Response bodies are still deliberately excluded from the exception (OAuth error bodies can echo tokens, `client_secret`, or `error_description` PII).
- **`DependsOnEvaluator.evaluate` gained a named `onError` argument, separating "expression absent" from "expression present but unevaluatable".** `defaultValue` continues to answer the first; `onError` answers the second. `FormBuilder` passes `onError: true`, so **a field whose `depends_on` this evaluator cannot parse is now SHOWN rather than hidden.** Hiding a field on an evaluator limitation destroys data — a hidden field is stripped on submit, so the field was invisible *and* unsaveable — while showing one merely clutters the form. Existing calls are unaffected; the argument is optional.
- **`DependsOnEvaluator.evaluate2` gained a named `onError` argument and now forwards it.** It previously delegated as `evaluate(expr, data)`, silently taking the `true` default for every caller. The argument is optional and defaults to `true`, so the signature stays source-compatible — but **a host calling `evaluate2` for `mandatory_depends_on` or `read_only_depends_on` should pass `onError: false`**, which is what the SDK's own callers now do. See *Fixed*.
- **`OAuth2Helper.refreshToken` now THROWS rather than returning a response that is not a usable token.** A return means "there is a live access token"; a 200 carrying an RFC 6749 `error`, or a 200 with no `access_token`, now raises `ApiException` instead of yielding an `OAuth2TokenResponse` whose `accessToken` is `''`. Only the RFC 6749 error **code** is carried on the exception (in `details`) — `error_description` and the rest of the body stay out, for the same PII reason the status-only rule already documents. A host calling this method directly must handle the exception where it previously received an empty-token response; the previous behaviour was not usable in any case.
- **`DoctypeService.bulkGetWithChildren` now throws instead of returning an empty list when a `2xx` body is not `{"message": [...]}`.** Previously any unexpected shape — including the raw body string `RestHelper` returns for an unparseable `2xx` — became an empty result indistinguishable from "every requested name was denied". See *Fixed* for why that was a data-loss vector. A host calling this method directly must now handle `ApiException` (status `502`) where it previously received `[]`. A genuinely empty `{"message": []}` still returns `[]`.

### Fixed

- **A completed upload could resurrect an attachment the user had discarded.** The writeback was `WHERE mobile_uuid = ?`, unconditional on the column's current value, so an upload already in flight when the user discarded (or re-picked) would rewrite its url into the field afterwards — restoring a removed attachment, or letting an old upload claim a new pick's slot. It is now conditional on the column still holding that row's `pending:<id>` marker, so it matches nothing once the user has changed the field. Every legitimate path still matches, including crash-then-resume.
- **Clearing an attach field left its queued attachment behind.** `LocalWriter` dropped the prior `pending_attachments` row only when a new local path replaced it, so emptying a field left the row alive with the column cleared — and the push gate then blocked that document indefinitely on an attachment nothing referenced. Clearing now drops the row and its staged file. Scoped to null/empty only: a synced field holds `/files/…` and its `done` row is the writeback backstop.
- **A value supplied after a field's first build never rendered.** Both attach fields resolved their display value from the form state alone once an explicit clear became representable, but `initialValue` applies once and a field's key is stable, so a document loaded asynchronously left the field blank. They now use `hasInteractedByUser` to tell "the user cleared this" from "never touched" — the only signal that distinguishes them.
- **`clearMediaCache()` deleted un-uploaded attachments.** It delegated to a whole-store wipe, so a host wiring an obvious "Clear cached media" control silently destroyed every staged file — the only copy of an attachment that had not uploaded yet. It now clears the `cache/` directory and the `media_cache` index only, and cannot touch `outbox/` or `pending_attachments`. `logout(clearDatabase: true)` is now the only path that clears staged files, where that is the intended security behaviour.
- **Staged attachment files leaked whenever a pick never reached a save.** Staging happens at pick time, but the only thing that deleted a staged file was keyed to a `pending_attachments` row, which is not created until save. So picking twice without saving left both files on disk, and abandoning or crashing out of a form stranded one — in `outbox/`, which is deliberately never evicted, so nothing but a logout ever reclaimed them. Replacing a field value now deletes the file it replaces, and `sweepOrphanedMedia()` reclaims the rest.
- **A `pending:<id>` marker could be written into Frappe verbatim as an attach-field value.** The marker was stored in `docs__<doctype>` at save time and nothing ever rewrote that column, while `PayloadAssembler` rebuilds the payload from `docs__` on every dispatch — so resolution depended entirely on the pending-attachment query returning the row, and that query selected only `pending` / `uploading`. Once a row left those states the marker resolved to nothing and `inlinePayload` shipped it as-is. Three ways in, all reproduced against the real `LocalWriter` → `AttachmentPipeline` → `PayloadAssembler` path: (1) the upload succeeded, the parent POST then failed, and the user retried; (2) the upload was terminally refused, the row went `blocked`, and the user retried — this path **reported success**; (3) any `TimestampMismatchError`, via `_autoMergeAndRetry`'s recursion, with no user action at all. The fix makes a `server_file_url` **committed to SQLite** the correctness boundary: the resolved url is written back into `docs__` in the same transaction as the state transition, so payload assembly reads an ordinary `file_url`. Upload and doc-push are now independent commitments — once committed, the file is uploaded permanently regardless of whether the parent ever syncs, and no later attempt re-uploads it. A parent document may now only push when **every** one of its attachments is `done`; anything else throws `BlockedByUpstream` naming the file and field rather than a row id.
- **Staged attachment files leaked on every document-removal path.** `hardDeleteLocalMirror`, the offline-cancelled-INSERT branch and the tombstone branch each deleted the `pending_attachments` rows and left the files behind, and nothing else ever reclaims that directory — so a discarded survey leaked its photos permanently. All three now route through `deleteForTopParent`, which deletes the files with the rows. The same gap existed on re-pick, where replacing a field's attachment stranded the prior bytes; the replacement is guarded so a re-save that re-supplies the same staged path cannot delete the file it is about to queue. The media cache is deliberately untouched by all of these: cached bytes are keyed by `file_url` and may be shared between documents, so their lifetime is governed by eviction and wipe, never by one document's.
- **`upload_file` was called with three field names Frappe does not read.** The SDK sent `dt` / `dn` / `filename`; `frappe/handler.py` reads `form_dict.doctype` / `.docname` / `.file_name` — verified against 16.25.0, 16.26.3 and 17.0.0-dev. The `dt`/`dn` branch was unreachable in-tree (no call site passed them) so no released behaviour changed, but it was a trap for the next caller, who would have received a File row that looked attached and was not.
- **Every uploaded attachment landed on the server named after an internal uuid.** Three places discarded the user's filename and all three had to change together: staging renamed the file, the enqueue recorded that renamed basename, and `RestHelper.uploadFile` sent it as the multipart part name. The last is load-bearing — Frappe reassigns `filename = file.filename` from the multipart part whenever a file part is present, so the part name, not `form_dict.file_name`, decides the stored name.
- **The on-device media store survived logout and data wipe.** `AppDatabase.clearAllData()` drops `pending_attachments` and `media_cache`, but the files live outside SQLite and nothing cleared them — so on a shared device one user's private survey photos stayed readable on disk after the next sign-in. `FrappeSDK.logout(clearDatabase: true)` now clears the store. Note this is destructive by design: it also clears staged picks, which are the only copy of any attachment that never uploaded.
- **`pending_attachments.size_bytes` and `.mime_type` were never populated.** Both columns existed in the schema, the model and the DAO, and the save path never passed either — so quota, eviction and progress had no data to work from. Both are now derived at save time from the staged file. `mime_type` comes from an extension table rather than a new dependency, and an unrecognised extension stays null rather than being guessed.
- **A fresh install recorded `sdk_meta.schema_version` from a hardcoded literal that had drifted from `AppDatabase._version`.** The `onCreate` path wrote `6` directly, so bumping the version left a new install reporting 6 while `PRAGMA user_version` said 7. It now threads the `version` argument, making the two impossible to disagree on the next bump.

- **HTTP 417 was treated as a transient refresh failure, so a dead session retried forever.** Frappe rejects an unredeemable refresh token with a 417 `ValidationError`, not a 401. Classifying that as transient meant the client never cleared the token, never surfaced an expired session, retried indefinitely, and tripped the backend's per-user rate limiter — with no route to re-login. Now definitive: tokens are cleared and `SessionHealth.expired` is published. See *Added* for why the widening is scoped to the refresh call site only.
- **The OAuth refresh leg wiped tokens on ANY error, including while offline, and never reported the session as expired.** Two independent faults in one `catch`. (1) A transport failure destroyed a perfectly good OAuth grant — worst at launch, where opening the app with no connectivity stranded the user behind a login screen they could not reach. (2) A *genuinely* dead grant was wiped but `sessionHealth` was left untouched, so no host was ever told to prompt. Both legs (`restoreSession` and the reactive fallback) now classify with **`isDefinitiveOAuthRejection`**: only a definitive rejection clears tokens and publishes `expired`; a transport failure or 5xx keeps the grant. This required `OAuth2Helper` to carry the status on its exception at all — see *Changed*. **Correction to an earlier revision of this entry, which said these legs classify with `isDefinitiveRefreshRejection`:** that predicate's `{401, 403, 417}` set is the *mobile* leg's, and it matches nothing the OAuth endpoint emits for an expired grant — so the fix inverted into never wiping. See the dedicated entry below.
- **A guest fallback on the mobile-configuration fetch could hide an expired session behind a populated workspace.** `resyncMobileConfiguration` retries `mobile_auth.configuration` unauthenticated when the authenticated call fails, because the deployed endpoint's authenticated filter can raise a `PermissionError` instead of returning a filtered list. The retry was reached from an **unscoped** `catch`, so it also fired on 401 and on transport failures: a dead credential was answered with the **unfiltered guest list**, and `_updateMobileFormDoctypes` marked every entry `isMobileForm: true`. The unreadable doctypes then entered the closure, 403'd, were demoted by the terminal-refusal guard above, and were re-promoted on the next launch — manufacturing exactly the churn that guard exists to suppress. The fallback is now scoped to the two statuses a server-side permission filter can refuse with — **403 and 417** (Frappe maps `PermissionError` to 403, but a `has_permission` hook raising through a bare `frappe.throw()` surfaces as `ValidationException`/417); **401, every 5xx and transport failures propagate**. The 417 is included deliberately rather than defensively: the commit that added this workaround recorded the symptom but not the observed status, and scoping to 403 alone would make the method throw on a deployment where it previously recovered. Widening is safe because it is scoped to this one call site — a 417 from a configuration fetch is not a statement about the credential, and nothing on this path wipes a token. Additionally, the guest list — and *only* the guest list — is scoped against the locally-synced permission matrix before use. That subtraction is **deny-only**: a doctype is dropped solely when a permission row exists *and* `read` is 0. A doctype with no row is kept, because `PermissionService` defaults a cache miss to *allow*, so a positive filter would be a no-op once permissions sync and would empty the workspace on a first launch before they have. The authenticated response is never intersected — it is already server-scoped, and a stale local matrix must not subtract from it.
- **Transport failures climbed the refresh backoff ladder, gating refreshes for up to 15 minutes after connectivity returned.** The ladder exists to protect the backend's per-user rate limiter; a request that never reached the server cannot have spent any of that budget. Time spent offline nonetheless ratcheted the gate to its maximum rung, and nothing lowered it on reconnect — the user was back online and still could not refresh. A transport failure now arms a single **non-climbing** 30-second rung and does not consume a ladder step. It never *shortens* an existing cooldown, so an offline blip mid-429-lockout cannot hand the client an early retry.
- **`extractEvalDocField` returned a whole expression as a fieldname.** The bare-`doc.field` fast path compared the expression against a helper that merely strips a leading `doc.` without checking the remainder is a legal fieldname. For `doc.a && doc.b` the remainder reassembled to the original string, the equality held, and `a && doc.b` came back **as a fieldname**. No such field exists, so the dependent-field lookup found nothing and the affected Link picker silently **stopped filtering** — presenting as "no filter configured" rather than as an error, which is why it went unnoticed. The fast path is now gated on the fieldname *shape*, so any multi-term expression falls through to the first-`doc.<field>` regex as intended. A separate earlier fix in this release stops a trailing `;` from being mistaken for a complex expression (`eval:doc.x;` still fast-paths).
- **A child-table `.some()` `depends_on` expression silently evaluated to false.** Desk compiles `depends_on` with `new Function`, so `eval:doc.some_table.some(r => r.field === 'Other')` evaluates natively there. This evaluator split expressions as strings with no notion of iterating a child table, so it returned false — and any field gated that way was both **invisible and unsaveable**, since a hidden field is stripped on submit. `.some()` over a child table is now understood. Returning a silent false for an expression the evaluator does not understand was the worst available answer, being indistinguishable from a correctly-evaluated false; the companion `onError` change in *Changed* addresses the general case. **Correction:** an earlier revision of this entry read as though that closed the general case. It did not — `onError` reached only one of its three call sites until the fix recorded below.
- **`depends_on` expressions with a leading `!` never evaluated.** A leading logical NOT fell through to the truthy fallback, which looked the whole expression up as a literal fieldname (e.g. `'!doc.__islocal'`), found nothing, and returned `false`. **Behaviour change:** fields using the standard `read_only_depends_on: eval:!doc.__islocal` idiom — "lock this field once the document is saved" — previously stayed editable after save and now correctly become read-only. The branch runs after the `&&` / `||` splits so `!a && b` still splits first, and is guarded against `!=` / `!==`.
- **Rating fields were stored on the wrong scale.** Frappe persists a Rating as `stars / max_stars` — a 0..1 fraction, not a star count (ten of ten is `1`; three of five is `0.6`), with `options` carrying the star count. `RatingField` emitted an integer star count, so two things were wrong at once: a rating authored through this SDK was written on a **different scale from every other Frappe client**, and a value authored elsewhere (`0.6`) failed to parse as an int and rendered as **zero stars**. The widget now stores and emits a double in 0..1 and renders `round(value * maxRating)` filled stars; re-tapping the last filled star clears the rating, matching the web SPA. Conversion lives in pure statics (`starsFromStored` / `storedFromStars` / `maxRatingFor`). Rating also moves from the integer column types to the real ones — the column was declared `INTEGER` while holding fractions. SQLite's type affinity preserves a value it cannot losslessly convert, so nothing was corrupted in practice and **existing installs keep their `INTEGER` columns and need no migration**, but the declared type contradicted the data and would truncate under a stricter engine. **See *Notes for upgraders* — this changes the meaning of already-stored values.**
- **A missing `docstatus` compared as `null` instead of `0`.** In Frappe a document always has a `docstatus` — `0` while it is a draft — so desk treats `eval:doc.docstatus === 0` as true on a new document, but client-assembled form data does not always carry the key. **Behaviour change:** draft-only `depends_on` / `mandatory_depends_on` / `read_only_depends_on` rules previously evaluated `false` and now fire, so affected fields may newly appear, hide, or become mandatory. Only `docstatus` is defaulted; every other missing field still reads as `null`, and the truthy fallback is unchanged.
- **A fully permission-filtered page no longer freezes a doctype's incremental watermark.** `PullPageFetcher` recognised an all-denied page as "skip, not end-of-stream" only in *initial* mode, where `limit_start` can step over the block. Incremental pulls pin `limit_start` at `0`, so the fetcher returned the cursor unchanged, `PullEngine` broke out of the drain, `markComplete()` re-persisted the identical watermark, and the next sync issued the byte-identical query — the doctype's watermark froze **permanently** and every document behind the denied block became unreachable, recoverable only by clearing the cursor. `DoctypeService.listFullDocsPage` now also reports the *scanned* name window's high-water `(modified, name)` (its inner name query projects `modified` alongside `name`), and the fetcher advances `modified` past a fully-denied window and reports it as a skip so the engine keeps draining within the same cycle. The skip is checkpointed, so a failure on a later page no longer discards it and re-scans the denied block next cycle. The advance is strictly-greater-only: a window whose scanned max **equals** the incoming cursor (≥ `pageSize` denied rows inside one `modified` second) still stops, since `>=`-based paging offers no way forward there — and `name` is never advanced without `modified`, because bumping it alone would leave the next request identical *and* would make `SyncService`'s tie-group skip drop readable rows. A deployment that refuses to project `modified` yields a null watermark and falls back to the previous stop-and-retry behaviour — inert, not broken. `SyncService`'s own paging is unaffected: it advances `limit_start` in both modes and was never subject to this. **API note:** the record returned by `listFullDocsPage` gains `scannedMaxModified` / `scannedMaxName`; callers that read its fields by name need no change.
- **A table that acquires the server audit columns via the per-pull reconcile now also acquires its `owner` index.** `buildParentSchemaDDL` (fresh installs) and `AppDatabase._migrateV5ToV6` (upgrades) both create `ix_<suffix>_owner`, but `OfflineRepository._reconcileParentTableSchema` — the belt-and-braces path for tables created between an upgrade and the next pull, or provisioned outside the migration path — backfilled the three columns and stopped there, so exactly those tables kept the full scan that index exists to remove. (The 2.0.0-beta *Performance* note's "fresh and upgraded installs" claim now holds for all three provisioning paths, under one index name rather than two.) The index is created at both exits of the reconcile and is deliberately **not** gated on "we just added `owner`" — a host that provisions its own table *with* the columns but *without* the index lands in the same place. `IF NOT EXISTS` makes the per-pull re-run free, and the statement runs only after the `ALTER`s succeed, so an index failure is logged by the existing handler instead of failing the pull page.
- **A malformed bulk-fetch response is no longer reported as "every document was denied".** `bulkGetWithChildren` returned an empty list whenever a `2xx` body was not `{"message": [...]}`, with no exception and no log. `RestHelper` hands back the raw body **string** for any `2xx` whose `jsonDecode` fails, so a truncated or proxy-mangled response on the largest payload the SDK requests — up to 200 full documents plus child rows — landed in exactly that branch. `listFullDocsPage` then reported zero docs with a non-zero `namesScanned` and a valid scanned-window watermark, which is **byte-identical to a legitimately all-denied window**. Combined with the incremental skip above, that advanced the watermark past rows which were readable and had never been fetched, and checkpointed it: permanent silent data loss, recoverable only by clearing the cursor. The method now throws (`502`, deliberately not `404`, which the caller degrades to per-name `GET`s) so the page fails, the cursor is left untouched, and the window is retried on the next cycle. A genuinely empty `{"message": []}` is unchanged and still means "every name denied" — that distinction is the whole point, and it is pinned by tests in both directions. **The safety property this restores:** a zero-doc page may only move the watermark when the zero is a permission decision, never when it is a failed fetch.
- **The OAuth leg could never report a session as expired, because Frappe answers a dead grant with 400.** `frappe.integrations.oauth2.get_token` returns the oauthlib error object in the response body and forces `http_status_code = 400` on it (`invalid_grant` is not a `FatalClientError`, so it never reaches the JSON error responder, and oauthlib's own status for `InvalidGrantError` is 400 too). The refresh leg classified on the *mobile* leg's `{401, 403, 417}`, which that endpoint does not emit for expiry — so a permanently dead grant kept its tokens, published `degraded` instead of `expired`, never latched the dead-session flag, and climbed the backoff ladder to the 15-minute rung indefinitely; the token-clearing path was unreachable for ordinary expiry. At launch the user got a login screen with a dead grant still in secure storage and `sessionHealth` reading `healthy`. Now classified by `isDefinitiveOAuthRejection` (see *Added*). **This is the inverse of the fault the same release fixed in the other direction:** the previous behaviour wiped on *any* error including while offline, and correcting the exception type so the status survived was necessary but not sufficient — the predicate then discarded it.
- **`mandatory_depends_on` / `read_only_depends_on` could still fail CLOSED in two of three places.** `evaluate`'s contract is that an unevaluatable expression must answer `false` for these two — erring towards required blocks Save with nothing the user can do about it, and erring towards locked makes a field permanently uneditable. Only `FrappeFormBuilder`'s widget-level gates obeyed it. (1) Reactive mode (`FormController`) goes through `evaluate2`, which dropped the argument, so **the recommended engine took the harmful default for both expressions.** (`evaluate2` now forwards its `defaultWhenEmpty` as the error default, so the two questions get one answer — see the API note under *Changed*.) (2) The meta-driven mandatory sweep called `evaluate` bare, so it disagreed with `_isFieldRequired` seventy lines above it in the same file: the widget marked the field neither required nor asterisked, and the sweep blocked Save on it — a dead Save button with no visible cause, the same shape this release fixes for empty child tables. Not a regression (the base branch returned `true` unconditionally), but not closed either until now. The error-default parameter — named `onError` at the time, `defaultOnError` now — also had **no test coverage at all**; all three sites are now pinned by tests that fail if any one is reverted.
- **A launch-time OAuth refresh failure armed no cooldown.** `restoreSession`'s transient branch logged and fell through, unlike the reactive path, so the first reactive 401 after a failed launch refresh re-attempted immediately — re-entering the refresh storm the backoff gate exists to prevent, through the one path that runs before the user has done anything. It now arms the same cooldown. Relatedly, a successful **API-key** restore now clears session health: that credential does not expire and must not inherit `degraded`/`expired` from an OAuth grant it never uses.
- **A fully-filtered incremental window that cannot advance is now logged instead of silently reporting end-of-stream.** `>=`-only paging has no way past a denied block of `pageSize`-or-more rows that all share one `modified` value, so the watermark legitimately stays put — but any readable row behind such a block is then never mirrored, which from the host's seat is indistinguishable from loss. `PullPageFetcher` now emits the doctype, the scanned count, the cursor and the window max at that point. The limitation itself is unchanged.
- **`link_filters` authored with a trailing semicolon resolved to a fieldname that no form data holds.** `DependsOnEvaluator.extractEvalDocField` stripped a leading `doc.` but not a trailing `;`, so `eval:doc.state;` — a spelling Frappe authors use routinely — returned `state;` instead of `state`. `LinkOptionService` then looked that key up, never found it, and the dependent Link field lost both its filter and its "select X first" hint. A Frappe fieldname can never contain `;`, so the strip cannot mis-fire. The bare-reference fast path is now matched against the *stripped* form rather than inferred from "the string changed", because the strip alone made a complex expression that merely ends in `;` (e.g. one wrapped in `.replace(...)`) look like a bare reference and return whole. `evaluate` needed no equivalent change — `js_expression.dart` already parses a trailing `;` as expression-statement punctuation.

### Added

- **Attachments can be discarded.** `Attach` / `Attach Image` / `Image` fields show a remove control whenever there is a value and the field is editable; previously an attachment could only be replaced, never removed, even on an optional field. The field clears before the local bytes are reclaimed, so a failed reclaim leaves an orphan the sweep collects rather than leaving the attachment in place while the user believes it is gone. A staged file is deleted, a queued row is dropped at save, and a synced file is left on the server — the same treatment delete and re-pick already give it.
- **`ImagePickSource` — a host hook choosing gallery, camera, or both** for image fields. Global across doctypes and fields and read live, so it can be flipped from a setting without rebuilding; null means both, so existing hosts are unaffected. `camera` removes the gallery route entirely, which is the point when a fresh capture is required and a stock image must not be submittable. Applies to `Attach Image` / `Image` only — `Attach` uses the system file picker, which has no such distinction.
- **`FrappeSDK.mediaStoreUsage()` and `FrappeSDK.sweepOrphanedMedia()`.** Usage reports staged bytes, cached bytes, and how much is reclaimable right now, so a host can show "1.4 GB — 240 MB reclaimable" instead of offering to free an unknown amount. The sweep deletes only staged files that no queued attachment references and that were not staged in this session — both guards exact, no age heuristic — so a pick sitting in an open form is never at risk. It never throws, and deletes nothing if the referenced-set query fails, because an empty result must not be mistaken for "everything is an orphan".
- **Offline attachment previews, via an on-device media cache.** A new `media_cache` table and `MediaStore` index bytes by server `file_url`, so one set of bytes is stored once no matter how many documents reference it — Frappe dedupes uploads by content hash and returns the same url for identical content, so a per-document cache would have stored them twice and made deletion a reference-counting problem. Media uploaded by the **push** path becomes its own cache entry (the staged file is moved, not deleted), and media pulled from the server is cached the first time it is viewed online. An **online** pick is the exception: it uploads inline and discards its local copy, so previewing it later costs one download. `Attach` / `Attach Image` / `Image` fields render from disk when a cached copy exists, so an attachment opened once stays viewable offline, and a non-image attachment is handed to the external app from the cache instead of being re-downloaded on every open. Cache state is non-authoritative throughout: an entry whose file has vanished is treated as a miss and re-fetched, never as an error. **Automatic eviction is not part of this release** — the store grows until logout or an explicit clear.
- **`FrappeSDK.clearMediaCache()`.** Clears `cache/` and the `media_cache` index — nothing else — so a host can offer a manual "Clear cached media" control while automatic eviction is unbuilt. It deliberately **cannot** touch staged picks, which are the only copy of an attachment that has not uploaded yet; only `logout(clearDatabase: true)` clears those (see *Fixed*). Byte reporting is `mediaStoreUsage()` above, which replaced the `mediaStoreSize()` this entry originally named (see *Changed*).
- **Offline mode now defers attachment uploads, whatever the connectivity.** A pick made while offline-first mode is enabled is staged and queued even on a fully connected device. Previously the decision was driven by connectivity alone, so an online device uploaded inline — which made data entry wait on a round trip, and put the attachment outside the offline pipeline entirely: no `pending_attachments` row, therefore no push gate, no `rejected` state, no cache entry, and no record that the upload had happened, so a discarded draft left an orphaned `File` the SDK could not name. `AttachField` / `ImageField` / `FrappeFormBuilder` / `FieldFactory` gain an `isOfflineMode` callback and `resolvePickedAttachment` gains `offlineModeEnabled`; both default to "not offline mode", so a host that wires neither keeps the previous behaviour.
- **A pick-time attachment size guard.** `resolvePickedAttachment` refuses a file over `maxBytes` (default 10 MB, matching Frappe's stock `max_file_size`) **before** the durable copy is made, and both field widgets surface the real limit rather than a bare "too large". Previously nothing checked size anywhere on the upload path, so an oversized photo was accepted, queued, and failed at sync — which, before the marker fix above, is exactly the case that silently corrupted the document. Reading the true server limit would need `mobile_control` to expose it; until then a wrong default only ever refuses early, which is recoverable.
- **A terminal / transient split for attachment failures.** `AttachmentState.rejected` marks an upload the server will refuse every time (oversized, wrong type, not permitted) and is never auto-retried; `failed` stays transient and is re-armed on the next dispatch. Without the split, re-arming failed rows would retry a permanently unuploadable file on every push forever. Replacing the attachment creates a fresh `pending` row rather than resurrecting the rejected one, so it never inherits a stale retry count or error. Classification is based on the exception types the upload path actually raises — `ValidationException` on HTTP 417 (how `MaxFileSizeReachedError` arrives), `AuthException` 403 versus 401, `ApiException` by status — and anything unrecognised defaults to transient, because a wrongly-transient error costs one retry while a wrongly-terminal one strands the user's file.

- **`SessionHealth` and a notifier that publishes it — new public API.** `SessionHealth` (`healthy` / `degraded` / `expired`) is exported from the barrel; `AuthService.sessionHealth` and `FrappeSDK.sessionHealth` expose it as a `ValueNotifier`. The SDK **never wipes anything on the strength of this value** — hosts decide what to show. Prompt for re-login on `expired` (the stored credential was definitively rejected and has been cleared); stay quiet on `degraded`, which clears by itself once a refresh succeeds. `AuthService.expiredSessionEmail` carries the identity captured *before* the token row was deleted, so a host can pre-fill the prompt — it is best-effort on the OAuth leg and may be null there, so handle `expired` without an email. The notifier is deliberately **not** disposed by `FrappeSDK.dispose()`: that method leaves the instance reusable, and a host wiring the notifier into a long-lived auth gate would otherwise get "used after dispose" on the next rebuild.
- **`isDefinitiveRefreshRejection` — new exported top-level function.** Classifies a *refresh-token* rejection: true for 401, 403 and **417**. It is deliberately one status wider than the existing `isDefinitiveAuthRejection`, and the widening is scoped to the refresh call site — Frappe answers an unredeemable refresh token with `ValidationError: "Invalid or expired refresh token"`, surfaced as `ValidationException` (417), not 401. `isDefinitiveAuthRejection` must **not** adopt 417: it is Frappe's generic validation status, so a 417 from an ordinary document save would wipe a healthy user's tokens. 429 stays non-definitive on purpose — the rate limiter keys on the resolved user, so a lockout says nothing about whether the token is still good.
- **`isDefinitiveOAuthRejection` — new exported top-level function.** Classifies a rejection of an **OAuth 2.0 refresh grant**, which is a different question from the mobile leg's: true for `{400, 401, 403}`, or for an RFC 6749 §5.2 grant-refusal code (`invalid_grant`, `invalid_client`, `unauthorized_client`, `invalid_scope`) lifted out of the response body. **400 belongs here and nowhere else** — `get_token` forces it for a dead grant, while on `mobile_auth.refresh_token` a 400 is a malformed request, so neither `isDefinitiveRefreshRejection` nor `isDefinitiveAuthRejection` adopts it. **417 is deliberately absent** — that is Frappe's generic `/api/method` validation status, which this endpoint does not emit. `invalid_request` and `temporarily_unavailable` are excluded from the code set on purpose: a malformed token request is a defect in this SDK, not a statement about the user's credential, and must not log them out. Every 5xx and every transport failure stay non-definitive, so an offline client keeps its grant.
- **A refresh backoff ladder (30s → 2m → 5m → 15m, last rung repeating).** A failed refresh no longer retries on the very next request. Single-flight alone only deduped refreshes overlapping *in time*; every subsequent request wave started a fresh one, which is how one session produced 215 refresh calls and tripped the backend's per-user rate limiter. A 429 jumps straight to the maximum rung. **Transport failures do not climb the ladder** — see *Fixed*.
- **`PermissionService` reports permission cache misses.** Every `canRead` / `canWrite` / `canCreate` / `canDelete` / `canSubmit` defaulted to `true` when no synced row existed for a doctype, with no signal. A miss means the UI is gating on an assumption rather than the server's matrix, and because the server still enforces the real permission the symptom is a 403 *after* the user has filled in a form. All five checks now route through one resolver that logs the doctype and invokes an optional `onCacheMiss` callback. **The default is deliberately unchanged — still allow** — so this can be measured before a stricter default is considered. The constructor gains a trailing optional named parameter, so existing call sites are unaffected.

### Removed

- **`device_info_plus` dependency** — dropped, no replacement needed. Nothing in `lib/` or `test/` imported it; `DeviceTier` reads `Platform.numberOfProcessors` from `dart:io`. This also removes a native plugin from every consumer's build.
- **`sqlite3` direct dependency** — dropped. It was declared only for explicitness and was never imported; `sqflite_common_ffi` still brings it in transitively. Note that its resolved version is now governed by that transitive constraint rather than by `^3.0.0`, so a consumer importing `package:sqlite3` **without declaring it** may resolve an older major — declare it directly if you depend on it.

### Notes for upgraders

- **The attachment work in this release is now verified on a device, but not exhaustively.** 2338 tests pass and the three marker-corruption paths are pinned by regression tests driving the real save → upload → assemble path. A measured run on an Android 8.0.0 (API 26) device against a live Frappe v16 bench — documented in [attachments.md](doc/release-2.0/attachments.md) §16 — additionally confirms staging under the picked filename, zero pre-sync uploads under offline mode, markers never crossing fields or documents, resolution and writeback, the `File` relink onto the right document and field, the staged→cache move, and that `mform_attachments/` is gone after `logout(clearDatabase: true)`. **Still unexercised on hardware**, covered by unit tests only: offline capture, offline preview from `outbox/`, `BlockedByUpstream` on a gated document, the `failed` and `rejected` states, re-pick and discard reclaim, camera lost-capture recovery, and the `OpenFilex` handoff. Exercise those on your own hardware before shipping. Note also that a site with `strip_exif_metadata_from_uploaded_images` enabled re-encodes JPEGs server-side — lossy, and GPS EXIF is destroyed (§16.2). The Frappe-side field-name fix is verified against three Frappe checkouts' source, not against a live site.
- **Media storage is unbounded until logout in this release.** There is no automatic eviction: every attachment this device uploads, and every one it views online, stays on disk. `mediaStoreUsage()`, `sweepOrphanedMedia()` and `clearMediaCache()` exist so a host can expose usage, reclaim orphans and offer a manual clear in the meantime. If your users work with many photos on low-storage devices, wire that control before shipping rather than after.

- **Rating values stored by a previous version are re-interpreted, and `1` is genuinely ambiguous.** The old widget wrote an integer star count; this release reads and writes Frappe's 0..1 fraction. `starsFromStored` treats `n <= 1` as a fraction and `n > 1` as a legacy star count, which disambiguates every value **except exactly `1`** — one star under the old scheme, full marks under Frappe's. Nothing in the value can discriminate the two, so such a row now reads as **full marks**. This affects upgrades over an install that authored ratings through the old widget; fresh installs are unaffected. If you have stored ratings, decide whether to migrate them before shipping this release — the SDK does not attempt it, precisely because the correct answer for `1` depends on data the SDK cannot see.
- **A doctype can now disappear from the workspace mid-session.** The terminal-refusal demotion (see *Changed*) clears `isMobileForm` on a 403 or a non-gateway 5xx, and nothing re-promotes until the next login or `initialize()`. If your host caches `getMobileFormDoctypeNames()` or renders a workspace from it, expect the list to shrink within a session and re-populate on relaunch. Hosts that need a mid-session recovery path can call `FrappeSDK.resyncMobileConfiguration()` themselves.
- **A field whose `depends_on` cannot be parsed is now shown instead of hidden.** Forms carrying expressions this evaluator does not understand may display fields that were previously invisible. That is the intended direction — a hidden field is stripped on submit, so the old behaviour destroyed data — but it is a visible change to form layout, so review any form relying on an exotic `depends_on`.
- **Three fixes in this release are verified by tests and source review only — not on a device.** Stated plainly rather than letting a green CI run imply otherwise. (1) The token-refresh re-entrancy fix is proven by a test asserting the 401 interceptor does not fire on an unauthenticated call; that is **not** the same as proving the app reaches the login screen when a stored refresh token is rejected at launch. (2) The schema-v6 audit-column backfill is proven against the server's source — the bulk endpoint returns `doc.as_dict()`, which carries `owner` / `creation` / `modified_by` — but has not been exercised against a live site. (3) The iOS deployment floor was raised in both the podspec and `Package.swift`; neither integration path was built. If you consume this release, exercise those three paths on your own hardware before shipping.
- **The OAuth classification rests on Frappe's source, not on a live revoked grant.** That `get_token` answers a dead refresh token with **400** is taken from the handler forcing `http_status_code = 400` on any body carrying `error`, plus oauthlib's own status for `InvalidGrantError`. It has **not** been exercised against a live deployment with a genuinely revoked grant — the tests use a mocked client, which pins the classification and the state transitions but cannot establish what a given server actually returns. The predicate is deliberately built so it does not depend on a single answer: it accepts the RFC 6749 error code as well as `{400, 401, 403}`. If your deployment answers differently, the two arms are the place to look. The same caveat applies to the empty-`access_token` path.
- **The one-time full re-pull cost is an estimate, not a measurement.** Schema v6 clears every pull cursor (see the 2.0.0-beta *Notes for upgraders* below), so the first sync after upgrading re-pulls every doctype. No timing was taken on a representative dataset or a metered connection, so "budget for that cost" is guidance rather than a figure.
- The sync-cursor and index changes in this release are pure Dart and DDL with no platform surface, so the test suite is adequate proof for them; the caveat above is scoped to the three items named in it.
- **The session-health, refresh-backoff, OAuth-classification and terminal-demotion changes are likewise proven by tests and source review only.** They are covered end-to-end at the `AuthService` / `MetaService` / `PullEngine` level with a mocked HTTP client, which pins the classification and the state transitions — but a mocked 401/417/502 is not a live server, and none of these paths has been exercised against a real deployment or across a real connectivity drop. If you depend on the re-login prompt, the offline-token-retention behaviour, or the workspace shrinking on a terminal refusal, exercise them on your own hardware before shipping.
- **Two assumptions the incremental pull now rests on, stated so a deployment can check them.** Neither is new — both are inherent to `modified >=` watermark paging — but the fully-filtered-window skip makes the first one load-bearing in a new place. (1) **The server honours `order_by: 'modified asc, name asc'` on `frappe.client.get_list`.** If it does not, a page is an arbitrary subset of the matching rows, so every incremental watermark — the skip's scanned max *and* the ordinary applied-page max — can advance past rows that were never returned. This affects the whole mechanism, not just the skip. (2) **A doctype's `get_list` visibility is a subset of its per-document `check_permission('read')` visibility.** The closure pull resolves documents through the per-doc gate while `SyncService` uses plain `get_list`, and the two share one on-disk watermark. `frappe-mobile-control` itself registers no `has_permission` hook, but **any co-installed app that does** can make the per-doc gate stricter than `get_list`, in which case the closure pull can advance the shared watermark past rows `SyncService` would have mirrored. If you run custom permission hooks, verify this before relying on incremental pulls.
- **A denied block larger than a page and sharing one `modified` value still stops that doctype's pull.** `>=`-only paging has no offset to step over it. Nothing is lost, but readable rows behind such a block are not mirrored until something in the block changes; the condition is now logged with the doctype, the scanned count and the window max. `FrappeSDK.forceFullRepull()` clears the cursor if you hit it.

### Changed

- **BREAKING — `DependsOnEvaluator`'s error-default parameter changed shape.** `DependsOnEvaluator` is exported from `package:frappe_mobile_sdk/frappe_mobile_sdk.dart`, so this is public API, not an internal detail. `evaluate`'s `onError` is **renamed** to `defaultOnError`; `evaluate2`'s `onError` is **removed** outright — it now derives the error default from its existing positional `defaultWhenEmpty`, because both callers wanted the ABSENT and the PRESENT-but-unparseable cases to get the same answer, and keeping two knobs invited them to disagree. A call site passing `onError:` by name no longer compiles: on `evaluate` rename it, on `evaluate2` drop it (the third positional argument already carries the intent). Callers that never passed it are unaffected — `evaluate`'s default is still `true`.
- **`depends_on` is evaluated as JavaScript, not matched against string shapes.** This decides which fields are visible, mandatory and read-only, and which fields reach the save payload, so it is the most consumer-visible change in this release. `DependsOnEvaluator` previously matched a hardcoded list of expression shapes (`' == '`, `' && '`, `'[..].includes(doc.x)'`); anything outside them fell through to a truthy fallback that looked the whole expression text up as a fieldname, found nothing, and hid the field. Now the `eval:` body is parsed and interpreted, as Frappe Desk's `frappe.utils.eval` does. Newly working: `.length` / `.includes()` / `.some()` on multi-select and Table MultiSelect, compact expressions (`doc.a=='X'&&doc.b=='Y'`), `!doc.x`, ternaries, parenthesised operands, bracket access, `in_list` / `cint` / `flt` / `cstr`, and `parent.<field>`. Measured over every `depends_on` in the workspace doctypes (699 unique expressions × 253 data combinations = 176,847 evaluations), old vs new adjudicated by node running Frappe's exact `let out = <code>; return out` wrapper: 9,976 results change, and the new evaluator matches Desk on 9,720 of the 9,723 it can be scored against. `referencedFields` output is unchanged for every expression, so the reverse-dependency graph is identical.

  Five deliberate departures from strict JS, each covered by a test:

  1. `[]` is **truthy** under `eval:` (as in JS) but **falsy** in the bare `depends_on: "fieldname"` form, matching Frappe's `$.isArray(v) ? !!v.length : !!v`.
  2. Relational and membership operators bridge number ↔ numeric-string, because `FieldNormalizer` stringifies `Int` / `Float` / `Currency` / `Percent` while Desk holds real numbers. Strict JS would hide fields Desk shows. **The bridge covers the relational operators (`<` `>` `<=` `>=`), membership (`includes` / `in_list`), loose `==`, and arithmetic `-` `*` `/` `%` — but NOT `+` and NOT `===`.** `+` follows JS and concatenates when either operand is a string, so `eval:doc.a + doc.b > 40` with `a="5"`, `b="0"` yields `"50" > 40` → true where Desk computes `5 + 0` → false; `===` compares types strictly, so `eval:doc.a === 5` with `a="5"` is false where Desk holds a real `5` and says true. Both are known gaps rather than decisions, and are tracked for the follow-up alongside the `parent` threading work.
  3. An expression **missing** the `eval:` prefix stays a plain key lookup, as in Desk — it is not evaluated as JS.
  4. `===` bridges `bool` ↔ `0`/`1`, because `FieldNormalizer` turns a `Check` into a Dart `bool` while Frappe stores and Desk holds `0`/`1`. Without it `eval:doc.flag === 1` is true on load and false after the user toggles the box.
  5. `.pop()` returns the last element **without removing it**. A `depends_on` expression is a question about the document, so answering it must not edit the document — and `depends_on` is re-evaluated per field per change, so a mutating `pop` deleted a row per keystroke. This replaces a one-level defensive copy of every list in the eval scope, which was both too expensive (it ran on every evaluation) and too shallow (it did not reach `doc.rows[0].tags.pop()`, whose receiver is a nested list, so that kept mutating live child-table state). `pop()` appears once in the corpus as `split('.').pop()`, where the receiver is a temporary and the two semantics agree; only a repeated pop within one expression could tell them apart, and no expression does that.

  An expression outside the supported grammar no longer defaults uniformly to "visible/true": `depends_on` still defaults to visible, but `mandatory_depends_on` and `read_only_depends_on` default to `false`, so an unparseable expression can no longer make a field permanently mandatory with no way to satisfy it. Desk is not a precedent for `true` here — it raises `Invalid "depends_on" expression`.

- **Frappe standard fields are readable from `depends_on` in reactive mode.** `FormController` seeds `docstatus`, `name`, `owner`, `doctype`, `idx`, `__islocal` and `__unsaved` from `initialData` — they are not in `DocType.fields`, but `eval:doc.docstatus == 0` and `eval:doc.__islocal` are common in Frappe meta. A missing `docstatus` now defaults to `0` and a missing `__islocal` is derived from the absence of a `name`, both matching `frappe.model.get_new_doc`, so draft-only fields are visible and saved-only fields hidden on a new document. These keys are excluded from `buildSubmitData`'s payload while still being present in the scope it evaluates `depends_on` against. **Both derived std fields — the `docstatus` default and the `__islocal` derivation — are applied inside `DependsOnEvaluator`, not in any one caller's seeding, and they trigger on a null value rather than merely an absent key** — so they hold for `FormBuilderMode.legacy` (the constructor default, which never constructs a `FormController`), for both of the legacy save-path scopes, and for a null that arrives after construction. `{'docstatus': null}` is an ordinary way to assemble an unsaved doc, and `null == 0` is false, so a key-presence test left every such document with its draft-only fields hidden **and dropped from the save payload**. `__islocal` was the same defect one field over: derived in reactive mode only, so in the default engine `!doc.__islocal` read `!undefined` == true on a brand-new document — showing the saved-only fields Desk hides on create, and, for `read_only_depends_on`, **locking a field the user is there to fill in**. The general rule, for anything added to this set later: a std field the SDK *derives* belongs in the evaluator, where every engine passes through; one it merely passes through does not. Today that is exactly `docstatus` and `__islocal`; the other five are pass-through.
- **Single read path.** All list reads route through `UnifiedResolver`. DB-first with background refresh on connectivity; Link decoration via `LinkDecorator`.
- `SearchableSelect` updated to support launching `SearchableSelectDialog` when `pickerMode` is `LinkFieldPickerMode.dialog`.
- **`pullSync` guards child doctypes.** Doctypes with `istable=1` are skipped at the entrypoint — `frappe.client.get_list` does not permit listing them, and children arrive embedded in parent pulls.

- **Form-level cascade clears.** When a Link field changes, the SDK auto-clears dependent Link fields whose `linkFilters` contain `eval:doc.{fieldname}` references. Consumer `FieldChangeHandler` callbacks should add value-derivation only — the form owns cascade cleanup.
- **Local UUID resolution.** Values matching the v4-UUID shape resolve from `docs__*` only; the SDK never calls `getByName(...)` for UUID-shaped values, since server names never match the UUID pattern.
- **Conflict surfaces.** When a pulled row is newer than a local dirty/failed row, `PullApply` sets `sync_status = 'conflict'`. Resolve via `SyncController.resolveConflict()` with two actions: `pullAndOverwriteLocal` (apply server snapshot) or `keepLocalAndRetry` (requeue; runs `ThreeWayMerge` against the pre-edit base).
- **Mobile-UUID round-trip.** After a successful first push, `OfflineRepository.reconcileServerSave` attaches the server's `server_name` to the local row keyed by `mobile_uuid`, cancels pending outbox rows for the pair, and applies the full server snapshot so server-derived columns (defaults, formulas) land in the mirror.
- **`OfflineRepository`** constructor — `database` is positional; `localWriter`, `offlineMode`, `offlineModeNotifier`, `client`, and `metaFetcher` are named. When the effective offline mode is off, `create` / `updateDocumentData` / `deleteDocument` route to `FrappeClient` directly; `getDirtyDocuments` returns empty.
- **`OfflineRepository.createDocument`** — preserves an existing `mobile_uuid` from the payload rather than always generating a fresh one.
- **`OfflineRepository.getRowFromPerDoctypeTable`** — added for `fetch_from` offline resolution.
- **`UnifiedResolver`** — translates the `parent` filter column to `parent_uuid` for child-table queries. All constructor parameters are named: `db`, `metaDao`, `isOnline`, `backgroundFetch`, `metaResolver` are required; `offlineMode`, `offlineModeNotifier`, `client` are optional. When the effective offline mode is off, `resolve()` short-circuits to a REST passthrough (no DB read, no `LinkDecorator`, no background-refresh dedupe).
- **`LinkOptionService`** constructor — now takes `UnifiedResolver` and a meta-resolver instead of `FrappeClient`.
- **`SyncService`** — `client`, `offlineRepository`, `database` are positional; `getMobileUuid`, `offlineMode`, `offlineModeNotifier`, `pushRunner` are named. `pushRunner` is the production push driver (`FrappeSDK` wires it to `PushEngine.runOnce`); `pushSync` returns `SyncResult.empty()` and logs a warning if it's unset. Every public method (`pushSync`, `pullSync`, `pullSyncMany`, `syncDoctype`, `getSyncStats`) returns `SyncResult.empty()` (or zeros) when the effective offline mode is off. Adds the `SyncResult.empty()` factory.
- **`FrappeSDK.initialize()`** — reads the persisted offline-mode flag, resolves the session-bound mode via `_resolveBootMode`, and gates closure pull in `_initialMetaAndDataSync` accordingly. `autoRestoreAndSync` defaults to `false`; when `true`, restores session and runs post-login bootstrap.
- **`FrappeSDK.forTesting`** — accepts an `offlineMode` parameter (default: offline) so existing tests continue to exercise the offline path.

### Removed

- **`DocumentDao`** — deleted, no replacement. All single-bag CRUD is replaced by `OfflineRepository` + `UnifiedResolver`.
- **Legacy `documents` table** — dropped during the v2 → v3 migration. The single-bag JSON store is replaced by per-doctype `docs__<doctype>` tables. Drop is safe because `1.x` devices push before persisting, so there are no unsynced rows in `documents` at upgrade time.

### Schema

- **`AppDatabase._version` is `6`.** `sdk_meta.schema_version` is written in lockstep by both `_onCreate` and all upgrade paths.
- **Migration step `_migrateV2ToV3`** runs within one transaction: (1) safely add v3 + v4 column extensions to `doctype_meta` via wrapped `ALTER TABLE ADD COLUMN` (catches "duplicate column name"); (2) idempotently create system tables (`outbox`, `pending_attachments`, `sdk_meta`) with `CREATE TABLE IF NOT EXISTS`; (3) drop the legacy `documents` table and its indexes; (4) upsert the singleton `sdk_meta` row with `schema_version = 3`.
- **Migration step `_migrateV3ToV4`** (new — runs for all existing v3 installs): creates the `kv` table (offline translation cache, `PRIMARY KEY (lang, src)`) inside `AppDatabase` using `CREATE TABLE IF NOT EXISTS`; updates `sdk_meta.schema_version = 4`. Fresh installs also receive the `kv` table via `systemTablesDDL()`.
- **Migration step `_migrateV4ToV5`**: adds the two tamper-detection tables (`security_state`, `security_events`). Every statement is `CREATE TABLE IF NOT EXISTS` / `INSERT OR IGNORE`, so an interrupted upgrade is safe to re-run.
- **Migration step `_migrateV5ToV6`** (new): materializes Frappe's server-owned audit columns `owner`, `creation`, and `modified_by` as nullable `TEXT` on every existing `docs__<doctype>` **parent** mirror, via wrapped `ALTER TABLE ADD COLUMN`; updates `sdk_meta.schema_version = 6`. Fresh installs receive the columns from `parent_schema.dart`.
  - This has to be a **versioned** migration rather than relying on the per-doctype reconcile: `FilterParser` now emits real SQL for these columns instead of silently dropping the clause, so a table created by an older build would fail such a query with `no such column: owner`. The reconcile paths only run during a pull and the closure pull is connectivity-gated, so an app that upgrades and then starts **offline** would query the old schema first. `onUpgrade` runs inside `openDatabase`, before any query can execute — so no such window exists.
  - **Child** mirrors share the `docs__` prefix but never carry these columns (`child_schema.dart` does not emit them), so they are identified by the absence of the parent-only `sync_status` column and left untouched. This keeps an upgraded install's child tables from drifting away from a fresh install's.
- **Upgrade paths:** v2→v6 runs every step in order; each intermediate version runs only the steps it still needs; fresh installs skip all of them. Every path produces identical final schema.
- **Storage layers:**
  - **Per-doctype mirror** — `docs__<doctype>` tables with `mobile_uuid` PK, `server_name`, `sync_status`, `sync_op`, `push_base_payload`, and field columns. Children carry `parent_uuid`. Tables are **lazily created** on first pull via `OfflineRepository.ensureSchemaForClosure`.
  - **System** — `sdk_meta` (singleton row tracking `schema_version`, bootstrap state, offline mode, session user); `outbox` (operation log indexed by state + created_at); `pending_attachments` (file upload queue with retry); `kv` (offline translation cache).
  - **Per-doctype mirror parent tables** additionally carry Frappe's audit columns `owner`, `creation`, `modified_by` (nullable `TEXT`, server-written only — the SDK never fabricates them locally, and they are stripped from every outbound payload so a client cannot forge `owner`).
- Fresh installs and every upgrade path end in identical schema state (`schema_version = 6`).

### Fixed

- **`DependsOnEvaluator` — regex literals and escaped quotes were being rewritten.** `_normalizeOperatorSpacing` closed a quoted literal on any matching quote, so `"it\"s"` ended early and the remainder was operator-spaced; and it spaced the operators *inside* a regex, turning `.replace(/<br>/g, '')` into `.replace(/ < br > /g, '')`, which then matched the `' < '` comparison branch and returned a definite wrong answer. Backslashes now escape, and a `/` in a value position opens a regex copied through verbatim (after an identifier or `)` it is still division).
- **A permission cache miss is reported once per doctype, not once per check.** `canRead`/`canWrite`/`canCreate`/`canDelete`/`canSubmit` resolve independently on list and form build paths, so one unsynced doctype emitted five identical log lines and five `onCacheMiss` callbacks per build. Allow-vs-deny is unchanged; only the reporting is deduped, and it re-arms when the cache is written.
- **Parent-mirror detection no longer keys on `sync_status` alone.** A *child* doctype declaring a DocField literally named `sync_status` gets that column emitted, and was therefore misclassified as a parent by both `_migrateV5ToV6` and `getDirtyDocuments`. Both now also require `parent_uuid` to be absent.
- **`get_list` no longer sends a wildcard the server rejects.** Three star-expansion paths (no resolver, empty expansion, expansion threw) left `'*'` in the request, guaranteeing failure. It is now stripped; if nothing remains, `fields` is omitted and Frappe returns its default set.
- **Attachment and image failures are visible.** `sdkLog` is debug-only, so in release an upload failure left the field empty with no explanation. Both widgets now show a SnackBar, including on a denied camera/gallery/storage permission — the camera handler previously rethrew from `onPressed` as an unhandled async error.
- **A finished attachment download no longer opens over an unrelated screen.** `_AttachViewButtonState` had no `dispose()` and `OpenFilex.open` was unguarded, so navigating away during a large download still launched an external viewer. The file is now discarded once unmounted, and a self-created http client is closed.
- **A 403 pull refusal is reported as `deferred`, not `failed`.** Since the closure pull is no longer gated on client-side `canRead`, a genuinely forbidden doctype is requested every cycle and refused every time — an expected steady state that was surfacing as a permanent per-doctype error. Real faults (5xx, transport, schema) are unchanged.

### Performance

- **`owner` is indexed and its equality filter is sargable.** `IFNULL(owner, '') = ?` could not use an index, and none existed — `chooseIndexes` only proposes meta-derived columns and the audit trio is never in `meta.fields`, so `owner = <current user>` was a full table scan on the main isolate. `FilterParser` now emits the bare `owner = ?` for the three audit columns (equivalent for every realistic query; a NULL column is excluded either way), and an `ix_<table>_owner` index is created for both fresh and upgraded installs. `!=` deliberately keeps the wrapper, where a NULL owner *is* "not alice".
- **A Link value with no distinct title is cached instead of re-queried.** For a doctype whose `title_field` is unset — most of them — the resolved label is the name permanently, but that outcome was left uncached to stay retryable, so every grid cell re-queried on every build. The cache now distinguishes "resolved, no distinct title" (final) from "row absent" (retry).
- **The merged `depends_on` evaluation map is built once per build** instead of once per expression. Affects only the legacy path with `initialData` and a read-only field, which is the only case that allocated.

- **`DependsOnEvaluator` — quoted string literals were being rewritten.** `_normalizeOperatorSpacing` has a quote-aware loop, but its final global `replaceAll(RegExp(r' {2,}'), ' ')` ran afterwards and undid that awareness, collapsing runs of spaces *inside* string literals. Any Select option or Data value containing two consecutive spaces silently failed its comparison, mis-gating `depends_on` visibility, `mandatory_depends_on`, and read-only. `eval:doc.status == "In  Progress"` against `'In  Progress'` returned `false`. Space collapsing now happens inside the quote-aware loop, so quoted contents are byte-identical to the input.
- `DependsOnEvaluator` — a bare `>` preceded by `=` (a JS arrow function, `r => r.x`) was spaced into `r = > r.x`, which then matched the `>` comparison branch instead of falling through to the truthy fallback. Guarded.
- **`FilterParser` now executes `owner` / `creation` / `modified_by` clauses instead of rejecting them.** These audit columns were absent from the offline schema, so a clause referencing one threw `Unknown column` — such a filter was **unusable** offline, not permissive. Consumers worked around it by omitting the clause. The columns are now materialized (see **Schema**) and the clauses emit real parameter-bound SQL. Genuinely-unknown columns still throw. Child doctypes still throw for these columns, since `child_schema.dart` never emits them — whitelisting them for children would have generated SQL against a nonexistent column.
  - Equality and `LIKE` comparisons are wrapped in `IFNULL(<col>, '')`, so a row whose audit column is still NULL does **not** match an `owner = <user>` clause. (Range, `IN`, `BETWEEN`, `timespan` and `IS NULL` forms emit bare SQL and are unaffected.) `_migrateV5ToV6` therefore also clears every pull cursor, so the next sync re-drains each doctype and backfills the values — without that, incremental pulls (`modified >= cursor.modified`) would only ever populate rows whose `modified` advanced server-side, leaving the filter silently partial rather than obviously empty. To force a later re-drain by hand, call `FrappeSDK.forceFullRepull()`; do **not** use `forcePullAll()`, which excludes entry-point doctypes and would report success while the mobile-form data was never re-pulled.
- **Documents created offline were invisible in their creator's own list.** `LocalWriter` now stamps a local prediction on a device-created parent row — `owner` / `modified_by` = the session user, `creation` = now — so an `owner = <me>` filter finds the user's own draft before it ever syncs. The prediction is never sent to Frappe (these columns are stripped from every outbound payload and from the `ThreeWayMerge` base, so a client cannot forge `owner`), and server truth overwrites it from both directions: `PullApply` on pull and `ResponseWriteback` on a successful push. An UPDATE preserves the existing `owner` / `creation`; only `modified_by` moves. With no session user available the fields stay NULL, exactly as before.
  - `creation` is formatted `YYYY-MM-DD HH:MM:SS` to match Frappe's wire format. This is deliberate, not cosmetic: `creation` is a TEXT column compared with plain SQL, and `' ' (0x20) < 'T' (0x54)`, so an ISO-8601 `T` separator would sort after every server-supplied value on the same date and silently break `creation >= ...` range filters.
- **`ResponseWriteback` dropped the server's audit values.** It wrote back only `server_name` / `modified` / `sync_status`, so a freshly-pushed document kept its local prediction until the next full pull. It now also persists `owner` / `creation` / `modified_by` from the push response, guarded by a hoisted `PRAGMA table_info` check — an unguarded `UPDATE` against a table lacking the columns would throw *inside the push transaction*, rolling back the whole writeback and leaving the outbox to re-push a document the server had already accepted (duplicate-creation risk).
- `PullPageFetcher` — `_fieldsToRequest` built `{'name','modified'}` plus meta fieldnames, and the audit fields are never in `meta.fields`, so the primary closure pull never requested them. Left unfixed alongside the `FilterParser` change, an `owner = me` list would have returned **nothing**.
- **A required-empty child table blocked Save with no visible error.** Neither `ChildTableField` (`Table`) nor `TableMultiSelectFieldBase` (`Table MultiSelect`) is a `FormBuilderField`, so `invalidate()` was a silent no-op for both and the user got a dead Save button. Both now render an inline error, in the legacy mandatory sweep and in reactive mode. The reactive path subscribes to the controller's error listenable, which also *creates* the notifier — so a field that mounts after validation (a lazily-built tab) still receives the message on arrival.
- `FormController._validateField` — a whitespace-only value counted as PRESENT for a required field, disagreeing with the legacy sweep's trim-aware check. Aligned on the trim-aware semantics. `0`, `0.0`, and `false` remain "set"; an empty list remains missing.
- `DataField` — the implicit 140-char `Data` cap was enforced with the counter suppressed, so typing simply stopped with no explanation and no message. The counter now appears within 20 characters of the cap on editable fields, and stays hidden otherwise to match the web UI.
- `AttachField` — remote attachment downloads had no timeout and buffered the entire response into memory via `bodyBytes` (OOM risk on a large PDF or video), and the temp file was named from the attachment's basename, so two attachments sharing a basename collided and served stale bytes. Now streamed with a 30s timeout, a 50 MB cap enforced against both `content-length` and a running byte count, and written to a dedicated subdirectory under a URL-derived filename that preserves the extension. Partial files are deleted on every failure path.
- `ImageField` — the Android activity-kill camera recovery called `retrieveLostData()` before *every* capture. That cache is process-wide, so a photo captured for one field could be claimed by a different one, and the user's explicit tap to take a new photo silently restored an old one instead. Recovery is now gated on a persisted per-field marker (`retrieveLostData()` *clears* the platform cache, so a non-owning field must never call it), bounded to 30 minutes, and announces the restore instead of swallowing the tap.
- `ServerRejection.message` — re-ran `jsonDecode` on the raw body on every read. Memoized; the returned string is unchanged for every input, including the malformed-body and `Unknown Error` fallbacks.
- `DocField.displayLabel` — allocated its zero-width-character `RegExp` on every call, on widget build paths. Hoisted to a `static final`.
- `FrappeFormBuilder` — a `onFieldChange` handler patching the **same field that is changing** with a rewritten value (e.g. normalising `'hi'` → `'HI'`) crashed with an unbounded synchronous recursion (`StackOverflowError`) through the text field's controller notifications; independent of `cascadeProgrammaticChanges`. The self-key's widget patch is now deferred one frame (form data still updates immediately). Regression-tested for both flag states.
- `FrappeFormBuilder` — the deferred self-key echo now suppresses its `patchValue` → `onChanged` re-fire **regardless of `cascadeProgrammaticChanges`**. Previously the guard was raised only when cascading, so with the flag off a self-referential handler on a typed field (Check/Date/Rating, where `FieldNormalizer` changes the value's representation) re-fired every frame with no depth cap — an uncapped infinite hang (pre-fix a `StackOverflowError`). The synchronous cross-field echo stays cascade-gated. Regression-tested with a cascade-off Check field.
- `FrappeFormBuilder` — programmatic-cascade value-equality now compares operands numerically **on numeric fieldtypes** (`Int` / `Float` / `Currency` / `Percent` / `Rating`), so a representation-only change (e.g. `10` vs `"10.0"`) no longer triggers a spurious self-terminating re-fire. Non-numeric fieldtypes keep trimmed-string equality, so an opaque id like `"007"` is still a real change against `"7"`.
- `FormController.buildSubmitData` — a field gated on a Frappe standard field (`eval:doc.docstatus == 0`, `eval:doc.__islocal`) was rendered, filled in by the user, validated, and then **silently dropped from the save payload**. The std fields are stripped from the payload map, and that same map was reused as the scope for the visibility sweep, so `doc.docstatus` read as `undefined` there and the field looked hidden. A `Section Break` or `Tab Break` gated that way dropped every field beneath it. The sweep now evaluates against a scope that carries the std fields while the payload still excludes them.
- `FormController` — a missing `docstatus` now defaults to `0`, so `eval:doc.docstatus == 0` shows its field on a **new** document as Desk does (`frappe.model.get_new_doc` sets `docstatus = 0`). Previously the key was absent, `undefined == 0` was false, and every draft-only field was hidden on create.
- `FormController` — a missing `__islocal` is now derived from the absence of a document `name`, so the reactive form no longer behaves as though every document were already saved. Desk stamps `__islocal = 1` alongside `docstatus = 0` on a new doc and drops it once the doc has a name, and Frappe's own new-doc test is `__islocal or not name`. Previously `!doc.__islocal` read `!undefined` == true, which **showed** the saved-only fields Desk hides on create (`depends_on: "eval:!doc.__islocal"` is the most common form of this expression) and, under `read_only_depends_on`, **locked a field the user was supposed to fill in**. An explicit `__islocal` supplied by the host still wins.
- `js_expression.dart` — `doc.<key>` now resolves an own property before the `.length` special case. A DocType with a field literally named `length` (dimension fields — `length` / `width` / `height` — are routine) read `undefined` instead of the field's value, so `eval:doc.length > 0` was permanently false and the field permanently hidden.
- `DependsOnEvaluator.evaluate` — a null / empty expression and an `eval:` with an empty body returned a hardcoded `true` instead of the caller's `defaultOnError`. `mandatory_depends_on: "eval:"` is non-empty, so it reached `evaluate` and made the field permanently mandatory.
- `js_expression.dart` — two objects no longer compare equal under `==`. Both operands were coerced to primitives unconditionally, so `[] == []`, `{} == {}` and `doc.ms_a == doc.ms_b` on two multi-selects holding the same options were all true; JS compares same-type objects by reference and says false. Object-vs-primitive still coerces, so `['A'] == 'A'` stays true.
- `js_expression.dart` — `cint` / `flt` follow Frappe's `parseInt` / `parseFloat` semantics instead of Dart's whole-string `num.tryParse`, and `flt` strips number-group separators. `cint('12abc')` was `0` and is now `12`; `flt('1,200')` was `0` and is now `1200`; `flt(r'$ 500')` is now `500`.
- `js_expression.dart` — parse **failures** are cached alongside successes. A single unparseable `depends_on` was re-tokenized and re-thrown on every evaluation, i.e. per field per keystroke, which is the cost the AST cache exists to avoid.
- `DependsOnEvaluator` — an evaluation failure is now reported once per expression rather than on every evaluation (the gate is a bounded set, cleared at 512 entries, so a host synthesising unbounded expressions can see occasional repeats). The expression is static DocType meta and the failure deterministic, but `_computeUiState` runs per field per change, so one bad expression on a 60-field form emitted a log line — and, in the generic catch, an interpolated stack trace — on every keystroke.
- `system_tables.dart` — all `CREATE TABLE` statements use `IF NOT EXISTS`; `sdk_meta` seed uses `INSERT OR IGNORE` for migration idempotency.
- `pull_apply.dart` — conflict flag now only fires when the server `modified` timestamp is strictly after the local `modified` (previously flagged any dirty row unconditionally).
- `SyncController.pause()` / `resume()` — `syncNow` now checks the `isPaused` flag before running.
- `BaseField` — wrap field labels in `Expanded` and use `CrossAxisAlignment.start` to prevent horizontal `RenderFlex` overflows when field labels contain long text (Issue #52).
- `FrappeFormBuilder` — replace `SingleTickerProviderStateMixin` with `TickerProviderStateMixin` to prevent "Multiple Tickers" crashes, and utilize `mapEquals` deep comparison for `initialData` in `didUpdateWidget` to avoid unnecessary controller teardowns and state resets (Issue #72).

**Outbox state machine (feat/sdk-offline-phase2 — PR #76)**

- `PushEngine._drainOnce` supersede pass — extended to include `paused` rows alongside `failed`. A stale paused row from a prior terminal rejection is now cleaned up when a newer `pending` row covers the same `(doctype, mobile_uuid, operation)` tuple, preventing phantom errors in the UI.

- `PullApply.isOwnInsertRoundtrip` — when a ghost-success INSERT left `server_name NULL` and the user re-edited before write-back, the dirty-conflict guard was bypassed and local edits were silently overwritten on the next pull (data loss). Fixed by checking the outbox for any non-done, non-in_flight rows for the matched `mobile_uuid` before accepting the round-trip flag; if owed work exists, the flag is cleared and the normal conflict guard runs.

### Notes for upgraders

- All new constructor parameters are optional with sensible defaults; existing call sites continue to compile and run.
- Offline mode is **off by default**. To run as an offline-first client, deploy the `frappe-mobile-control` server release that flips `offline_enabled = true` on `Mobile Configuration` **before** upgrading the SDK on devices. An offline deployment that does **not** flip the flag will see clients persist `false` on first login and drain + wipe local data on the next launch.
- Token refresh does not refresh the offline-mode flag. Long-lived sessions stay in their previous mode until the user re-authenticates (password / OTP / OAuth / API key).
- Existing tests that use `FrappeSDK.forTesting` continue to default to offline. To exercise the online-only path in tests, pass `offlineMode: const OfflineMode(enabled: false, isPersisted: true)`.
- Downgrade is not supported. `sqflite` does not provide a downgrade hook; users cannot downgrade through the app stores.
- **Schema v6 runs automatically, and re-drains once.** `_migrateV5ToV6` executes inside `openDatabase`, before any query can be issued, so an app that upgrades and then launches with no connectivity is safe — no host action is required to get the *schema* right. The migration also clears every pull cursor so the audit columns get backfilled, which means the first sync after upgrading is a **full re-pull of every doctype** rather than an incremental one. Budget for that one-time cost on metered connections; correctness of the new `owner` / `creation` / `modified_by` filters depends on it.
- **Locally-created rows now carry a non-NULL `owner`.** If any host code treats `owner IS NULL` as a proxy for "not yet synced", that inference no longer holds — use `sync_status` or `server_name IS NULL` instead. A search of the SDK found no such consumer, but host apps reading the mirror tables directly should check.
- `FilterParser` now emits real SQL for `owner` / `creation` / `modified_by` on parent doctypes instead of throwing `Unknown column`. A query that previously failed on such a clause now succeeds and returns a correctly-scoped result, so a consumer that omitted the clause as a workaround should remove that workaround and expect a **smaller** result set. A filter on these columns against a **child** doctype still throws, because child mirrors do not carry them.

## [1.0.0] - 2026-04-01

### Added

- Initial stable release of **Frappe Mobile SDK** for Flutter (`frappe_mobile_sdk`).
- **Frappe API client** — authentication (password, OAuth, API key, mobile OTP), CRUD, file upload, custom methods, and query-style access via `FrappeClient`.
- **Stateless mobile auth** — `mobile_auth.login` integration with token persistence, session restore, and automatic token refresh.
- **Dynamic forms** — metadata-driven rendering from Frappe DocTypes (`FrappeFormBuilder`, list and document screens).
- **Offline-first data layer** — SQLite storage, offline repository, and bi-directional sync with conflict handling.
- **App guard** — `FrappeAppGuard` for server-driven app status, versioning, and force-update flows (requires [Frappe Mobile Control](https://github.com/dhwani-ris/frappe_mobile_control) on the server).
- **Translations** — load dictionaries from the server and apply to labels in forms and lists.
- **Workflows** — workflow state and transitions on forms when configured on the DocType.
- Example app under `example/` and in-repo docs under `doc/`.
